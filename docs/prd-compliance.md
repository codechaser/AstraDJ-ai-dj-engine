## Dashboard/history implementation status (2026-10-21)

The authenticated `GET /api/v1/dashboard/playback-history` returns only the caller's existing `Interaction` records and labels provenance as `self_reported`. It does not imply externally verified playback. `GET /api/v1/dashboard/lounge-history` returns ended Lounge summaries only when the caller is its Host or a persisted participant; invite codes and other participant identities are omitted. The Host ends a Lounge with the authenticated Socket.io `lounge.session.end` command. First join persists `startedAt`; end persists `endedAt` and one summary snapshot after pending queue writes are flushed (chat is already durable before acceptance). Duration, queue-event count, distinct battle count, chat count, and timestamped sentiment points are rebuilt from persisted sources. New sessions also persist unique-user presence edges and successful AI-question request IDs. Analytics sequence follows the atomic per-Lounge metric sequence; calculations include events inside the persisted session window, ignore late post-end events, collapse repeated battle IDs and question idempotency keys, and validate participant counts. End retries do not append summary events. Legacy sessions without `analyticsTrackingVersion: 1` report presence/question values unavailable. The API and Profile omit private user IDs, invite codes, and chat text.

The disposable MongoDB reconciliation fixture contains a 60-second session, four QueueEvent rows but one distinct battle ID, five user-level presence edges with a peak of two, two unique accepted AI-question keys (one retried request), and three sentiment messages. The persisted end summary and authorized history/analytics responses match the manually calculated values exactly. Full details and contracts are in `server/API.md#dashboard-history-and-lounge-analytics`.

## Multi-instance chat delivery and sentiment recovery (2026-10-28)

Chat remains Mongo-persisted before a successful socket acknowledgement. Before returning success, the service confirms a durable `chat.message` event in the existing Lounge coordination outbox and marks the stored message with its event sequence. The outbox projection reuses the stable per-Lounge `QueueEvent` sequence and existing gateway polling; each gateway emits only to local sockets joined to that Lounge. A failure after message persistence returns `CHAT_DELIVERY_UNAVAILABLE`, not success. Pending messages are repaired by active Lounge gateways, and outbox projection retries preserve the same event identity. Delivery is at-least-once internally, not exactly-once over Socket.IO. Optional `clientMessageId` handles submission retries; clients deduplicate delivered events by server `messageId`. Authorized history remains the missed-message recovery path on reconnect.
