## Dashboard/history implementation status (2026-10-21)

The authenticated `GET /api/v1/dashboard/playback-history` returns only the caller's existing `Interaction` records and labels provenance as `self_reported`. It does not imply externally verified playback. `GET /api/v1/dashboard/lounge-history` returns ended Lounge summaries only when the caller is its Host or a persisted participant; invite codes and other participant identities are omitted. The Host ends a Lounge with the authenticated Socket.io `lounge.session.end` command. First join persists `startedAt`; end persists `endedAt` and one summary snapshot after pending queue/chat writes are flushed. Duration, queue-event count, distinct battle count, chat count, and timestamped sentiment points are rebuilt from persisted sources. New sessions also persist unique-user presence edges and successful AI-question request IDs. Analytics sequence follows the atomic per-Lounge metric sequence; calculations include events inside the persisted session window, ignore late post-end events, collapse repeated battle IDs and question idempotency keys, and validate participant counts. End retries do not append summary events. Legacy sessions without `analyticsTrackingVersion: 1` report presence/question values unavailable. The API and Profile omit private user IDs, invite codes, and chat text.

The disposable MongoDB reconciliation fixture contains a 60-second session, four QueueEvent rows but one distinct battle ID, five user-level presence edges with a peak of two, two unique accepted AI-question keys (one retried request), and three sentiment messages. The persisted end summary and authorized history/analytics responses match the manually calculated values exactly. Full details and contracts are in `server/API.md#dashboard-history-and-lounge-analytics`.

## Overall implementation estimate

Estimated implementation progress is **about 60%** of the PRD's functional scope. This is an engineering estimate, not a PRD acceptance metric: the project now has the core MERN foundation, authenticated catalog/profile APIs, shared queue, acoustic matching, chat/sentiment, Soundclash, recommendations, grounded Q&A/segue, ended Lounge history, and frontend connections for supported paths. The estimate remains below completion because playback history is self-reported rather than independently attested, several profile/settings screens remain incomplete, some session analytics are `null`, AI retrieval is deterministic rather than generative, and deployment/load/accuracy acceptance evidence is incomplete. PRD behavioral KPIs and performance targets are not counted as achieved based on mocked tests or synthetic fixtures.

## Admin acoustic-profile management (2026-10-22)

The Admin-only `/admin/acoustic` screen searches catalog tracks, shows saved versus missing profile state, and lets an Admin create or replace the four-field acoustic profile for an existing track. `PUT /api/v1/tracks/:trackId/acoustic-profile` verifies the current database role and rejects missing fields, non-number/non-finite values, out-of-range BPM/energy/valence, invalid Camelot keys, and unknown fields with `400 VALIDATION_ERROR`.
