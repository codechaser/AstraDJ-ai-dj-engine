### Queue benchmark interpretation

Do not combine unlike measurements as though they were the same drift metric. The successful multi-room report's drift uses client callback timing as a render-callback proxy; its 108.143 ms P95 is already over target. The full browser-queue baseline uses actual Chromium pages for one room within a three-room/two-process load: n=5 all-client drift P95 3,980.6 ms; browser DOM-render spread P95 1,737.1 ms (n=7); server-receipt-to-last-client delivery P95 7,280 ms (n=73); acknowledgement P95 4,674.272 ms (n=73). It reported 956 missing receipts of 4,500 expected, 50 duplicate receipts, 338 queue-state divergences, 17 server-processing failures, three duplicate durable events, and one durable snapshot divergence. These are measurement-window observations; the artifact does not establish whether every late client event was permanently lost.

The later 50-user diagnostic used only five browser pages per room and socket clients for the remainder. It showed 30 browser render acknowledgements with P95 upper-bound 634.85 ms and zero observed losses/divergences in that run. It does not supersede the full-browser failure. The five-client smoke report has only five drift observations and cannot support a 50-user target.

The 2026-10-26 runtime JSON reports queue synchronization P95 at concurrency 1/5/10/20 as 75.119/145.621/326.481/475.500 ms, with 485/500 recipient-event observations absent by an 8-second deadline at concurrency 20. Later queue optimization reports are separate runs; inspect them as trend evidence only. The fresh benchmark:prd command failed during this audit and generated no current report.

## Security and data-integrity review

Positive evidence: bcrypt password hashing; access JWT algorithm/issuer/audience checks and TTL <= 1 hour; refresh tokens stored hashed and rotated; registration fixes role to Listener; HTTP and socket authentication middleware; server-side Host/Admin/Listener permission checks on implemented operations; Lounge membership checks; strict Express JSON size and route validators; chat sanitization; user-scoped history/preferences/recommendations; shared Mongo fixed-window rate limiting; Helmet; origin allow-list configuration; log redaction for Authorization/cookie/password; unique indexes and deterministic outbox sequence IDs. These were source-reviewed and relevant unit/Mongo tests passed.

Residual security limits: no deployment penetration test, TLS/reverse-proxy configuration review, production cookie/CORS validation, or remote Mongo authorization test was performed. Rate limiting is fixed-window (boundary bursts possible); correct client IP behind a proxy depends on trusted proxy configuration. The normal server/.env was intentionally not inspected. The worktree's server/.env.example is already modified; it was preserved.

No evidence in this audit supports a claim of a critical exploitable vulnerability. The benchmark failure is a verification harness configuration gap, not evidence by itself of a production authorization bypass. The 50-browser event/state discrepancies are a data-integrity risk under that tested local load and need reconciliation/mitigation before scale claims.
