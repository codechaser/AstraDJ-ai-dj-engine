## Feature selected

Host Lounge creation and invite joining were selected because the backend contract and authorized gateway existed, but the central Host journey was disconnected from the UI. That blocks the PRD's main live demonstration and is more foundational than polishing sample Home or album previews. The feature reuses the Queue screen, existing catalog/API client and Socket.io path; no new backend stack or visual system is introduced.

Acceptance path: a Host signs in, selects a catalog starter, configures vibe/capacity/BPM tolerance/Soundclash/AI verbosity, creates the Lounge, receives an invite code and connects to its queue; a same-browser reload can rejoin from the saved invite; a second authenticated Listener joins with the code and receives the same Now Playing snapshot. The Playwright test verifies the persisted Mongo Lounge fields and settings. The server remains authoritative for role, invite validity, capacity and membership.

## Acoustic taste profile and recommendation evaluation (2026-10-22)

The authenticated `GET /api/v1/recommendations/taste` endpoint and Profile panel compute preferences from the caller's persisted interaction rows and valid Track acoustic profiles. Full completions and likes have weight 1; an incomplete, unliked report weighs its reported duration fraction; a zero-second skip weighs 0. Invalid/missing acoustic profiles and malformed reports do not contribute. The profile needs two distinct eligible tracks; preference aggregation uses each track's strongest report once, while source-row counts and track/acoustic coverage are shown separately. This prevents repeats from silently multiplying a single track but cannot distinguish a legitimate replay from a retried report. Taste is recomputed at read time, not cached. The same profile threshold now gates the acoustic recommendation signal; qualified collaborative-only recommendation behavior remains available. Immediate segue hard constraints and its 50/30/20 weights are unchanged.

The initial one-profile fixture is retained as a small unit regression. The newer reproducible `npm run benchmark:prd` comparison uses three separate synthetic profiles, two training interactions and ten candidates per profile; see the acceptance benchmark section below for counts, holdout separation, baseline, and limitations. Its 0.60 result remains a curated-fixture calculation, not real-user effectiveness or statistically meaningful evidence, and does not establish the deployed PRD target.

Verification: root `npm test` — 18 passed, 0 skipped; backend `npm test -- --runInBand` — 13 suites passed, 110 tests passed, 7 opt-in Mongo tests skipped; backend `npm run test:integration` — 20 suites, 117 passed, 0 skipped; root `npm run test:e2e:catalog` — 3 Chrome tests passed, including reload and persisted-profile rendering through the real API on an isolated disposable Mongo database (the test interactions are submitted as self-reported test records, not browser playback). `npm run build` passed; `git diff --check` passed. ## PRD acceptance benchmarks (2026-10-22)

Reproduce all diagnostics with `cd server && npm run benchmark:prd`. It does not connect to MongoDB or use application/user secrets. The script's Socket.io benchmark starts a local server and 50 authenticated simulated clients in one process against an in-memory repository. The benchmark has no cross-machine clock synchronization, so queue drift is the range of local client callback-arrival times for the same broadcast, not a general network guarantee.

**Acoustic hard constraints:** 20 ranked decisions cover direct, half-time and double-time BPM relationships, same/adjacent Camelot keys including 12↔1 wrap, and same-number opposite-letter keys; each decision also includes bad-BPM, incompatible-key, and invalid-key decoys. Result: 20 decisions, 0 invalid outcomes, 100% rule compliance, 0 score-weight formula errors. Existing acoustic matcher unit tests additionally exercise inclusive ±8% boundaries and just-outside values for direct/half/double tempo. These are deterministic simulations, not production recommendation statistics.

**Sentiment datasets and measured results:** The 40-message diagnostic fixture was created after reviewing the original lexicon, so it is lexicon-aware and non-independent. Original baseline scored 32/40 = 80%; updated frozen rules score 36/40 = 90%. It remains a regression diagnostic only.

**Recommendation holdout:** three synthetic profiles, each with two seed training interactions, ten candidates, and three manually predeclared relevant candidate IDs withheld from recommendation input. Across users, 6 training interactions, 30 candidates, and 9 held-out relevant labels. `Precision@5` is relevant IDs in each user's first five divided by 5, micro-aggregated as 9 hits / 15 slots = 0.60. Popularity ranking uses separate synthetic cohort counts (not held-out labels) and scores 0 / 15 = 0.00. Labels intentionally describe acoustic neighbors, so the result is deterministic sanity data, not evidence that real users would find the items relevant. The number meets the numeric threshold only for this biased synthetic fixture; deployed PRD relevance remains unverified. Missing profiles are covered by the existing cold-start tests and do not receive fabricated acoustic values.

**Queue and transition timing:** in the latest observed local run, 50 connected WebSocket clients saw 20 identical queue-add states. Per-event cross-client receive-time range was P50 1.671 ms, P95 2.061 ms, max 3.182 ms; time from command start to last client callback was P50 3.447 ms, P95 4.794 ms, max 5.2 ms. These local numbers are below the 100 ms sync and 500 ms fan-out thresholds, but one process, localhost, and in-memory persistence do not establish normal-network or Mongo-backed performance.

Across 250 isolated in-process `requestSegue` calls using fake model repositories and the existing deterministic metadata fallback, latest wall time was P50 0.060 ms, P95 0.136 ms, max 2.712 ms. This excludes MongoDB, Socket.io, audio/outro scheduling, and browser rendering; it does **not** verify the PRD's end-to-end transition P95 <3 seconds. The current Chrome/Mongo test also confirms an actual media decision is prepared inside the outro window while the source track remains current, then natural media `ended` starts the next asset and leaves one matching durable transition event. Three accelerated 10× browser samples were 257.2, 354.9, and 586.1 ms (nearest-rank P95 586.1 ms, n=3); this is too few accelerated local samples to substantiate the KPI. API latency P95 <200 ms, repeated independent load runs, concurrent vote drift at 50 users, fan-out on a real network, and multi-replica behavior remain unmeasured.

Other gaps remain: six audio settings are saved-only/disabled, album relationships and catalog metadata are absent, and Admin provisioning is out-of-band. See the feature rows above for sentiment, recommendations, and performance limitations.

## Ranked remaining implementation priorities (2026-10-25)

1. **Improve and independently validate room sentiment** — the new frozen 90-message synthetic set rose from 53.33% to 76.67%, still below the PRD's 85% target; negative recall is 60%. Next evidence step is a consented, privacy-reviewed dataset labeled independently by multiple annotators, followed by additional rules only on separately allocated development data.
2. **Make Soundclash safe across process failures and replicas** — single-process persistence, restart recovery, duplicate-safe votes, and automatic opening are now covered; process-local serialization/timers and non-transactional winner/queue writes remain.
3. **Make Lounge queue and segue coordination robust across process failures** — pending selected track is persisted and the event log can recover transitions, but the full decision is process-local, QueueEvent plus Lounge update is not transactional, and multi-replica command serialization is absent.
4. **Close acceptance/evidence gaps** — collect sufficiently repeated, non-accelerated transition latency samples and document/demo complete multi-participant flows; existing three accelerated browser observations cannot substantiate `<3s P95`.

## Soundclash persistence, recovery and auto-open increment (2026-10-25)

PRD source: §6.1 says a Host or AI DJ opens a timed battle after Listener submissions to challenge the current Next Up track; §6.2 says the AI DJ or Host opens a timed vote among 2–4 submitted candidates, tallies in real time, applies the winner, and announces it. §7.2.1 lists battle/candidate data entities; §7.3.4 fixes the `lounge.soundclash.open` payload (`battleId`, `candidateTrackIds`, `closesAt`) and `lounge.soundclash.resolved` payload (`battleId`, `winningTrackId`). The source does not prescribe when auto-open occurs, the vote duration, vote-change behavior, tie handling, or whether those entities must be separate collections. The implementation keeps the existing event-log architecture and event payload contract.

The durable per-Lounge `QueueEvent` log now carries submitted/opened/voted/tied/resolved commands and is replayed to restore candidate list, one-vote-per-Listener tallies, battle status, and deadline. The deterministic auto-opener records an AI-DJ-attributed open after the second distinct valid Listener submission; it is product logic, not a connected AI model. The Host open command is retained and idempotent once open. Each accepted vote is persisted before state/broadcast. An ambiguous write acknowledgement is checked against the event's unique sequence and content before success is returned. On process restart, an open battle's deadline is re-armed and its votes are replayed. The UI explains the automatic trigger without redesigning the existing panel.
